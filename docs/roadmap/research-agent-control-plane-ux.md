# Research: What Makes a Developer-Facing Agent Control Plane Good (2025-2026)

Scope: GitHub Agents tab / Copilot coding agent, Cursor cloud agents + Slack, Devin (Cognition), OpenHands web UI, Google Jules (web + CLI), Sourcegraph Amp (threads), Factory Droids, Claude Code web app (claude.ai/code) and its hooks/skills/subagent model, plus open-source Claude Code config managers on GitHub. All claims are sourced; anything not directly confirmed in a source is marked **[unverified]**.

---

## 1. Onboarding: time-to-first-task, shipped defaults, repo vs personal config

**GitHub Copilot coding agent / Agents tab**
- Entry point is a global "Agents" button in the GitHub header, opening a panel that lists tasks already delegated plus a way to start new ones by picking a model and optionally a third-party or custom agent (github.blog/changelog/2025-08-19). A dedicated **Agents tab** was added per-repository in Jan 2026, showing "all sessions for the repository in one place" (github.blog/changelog/2026-01-26).
- Repo-level enablement is admin-gated: enterprises/orgs control access to "Copilot agent mode" via a policies page, and a repo owner grants the coding agent access to "all or some" repos from Copilot settings' new "Copilot agent" tab (search synthesis, docs.github.com/copilot). This is a real onboarding gate — a developer cannot self-serve without an admin having turned the feature on for the org/repo first.
- **[unverified]** exact shipped defaults (firewall rules, allowed MCP servers) per repo — GitHub's own agent-management doc explicitly does not cover default configuration, repo-vs-personal config split, or firewall rules (fetched directly; page silent on these).

**Cursor Cloud Agents**
- Hard onboarding gate: "a Cursor account admin needs to connect source control" (GitHub/GitLab/Bitbucket/Azure DevOps) before *anyone* can start a cloud agent (cursor.com/docs/cloud-agent). This is an explicit blocker to "minutes to first task" for a team — the first task requires an admin action, not just a developer action.
- Environment setup happens via `.cursor/environment.json`, with three onboarding paths: "agent-led setup, a saved snapshot, or a Dockerfile" — i.e., Cursor will attempt to auto-detect the dev environment the first time, then let you save it as a reusable snapshot ("Builds") so subsequent agents start pre-warmed (cursor.com/docs/cloud-agent).
- Config layering is explicit and three-tiered: **repo-level** `.cursor/hooks.json` and `.cursor/environment.json`; **personal/user-level** `~/.cursor/hooks.json` (note: personal hooks do *not* carry into cloud VMs, since those have no access to your local home directory — a real onboarding surprise); **org-level** "team hooks and enterprise-managed hooks" on Enterprise plans (cursor.com/docs/cloud-agent).

**Devin (Cognition)**
- First unit of reuse is the **Playbook**: "a custom system prompt for a repeated task," created the moment you notice you're repeating instructions across sessions — i.e., Devin's own onboarding advice is "run it ad hoc first, then graduate to a Playbook" rather than requiring upfront config (fast.io/resources/devin-ai-playbook-guide; docs.devin.ai). Cognition's own internal dogfooding blog says they use Playbooks for recurring, well-scoped infra jobs (Redshift ingestion, DB migrations, Stripe/Plaid/Modal integration) — i.e., playbooks pay off most for narrow, repeatable ops-style tasks, not general coding (cognition.com/blog/how-cognition-uses-devin-to-build-devin).
- A session exposes three raw surfaces up front — Shell, IDE, Browser — plus a unifying "Progress" tab (fast.io/resources/devin-session-tools-guide). This is a heavier default UI than a chat box; the trade-off is transparency for a steeper first-session learning curve.

**OpenHands**
- Ships as an ecosystem (CLI + GUI + GitHub App) on one shared "Agent SDK," with a chat-based web UI that visualizes the agent's live actions (proceedings.iclr.cc 2025 paper; openhands.dev blog Nov 2025). Recent web-UI work specifically targeted onboarding: an "onboarding checklist," an LLM provider-connection UI, and an "overview panel" — i.e., OpenHands' own team identified first-run friction (bring-your-own-LLM-key, unclear starting point) as a problem worth fixing in 2025 (openhands.dev/blog/introducing-the-openhands-software-agent-sdk).

**Google Jules**
- Public beta May 2025 → GA Aug 2025 with paid plans from day one; **Jules Tools** CLI + Jules API shipped Oct 2025 specifically to remove the "context switch to the browser" for developers who live in a terminal (developers.googleblog.com). This is a deliberate second onboarding surface added after the web-only launch — evidence that web-only async agents don't fit terminal-native workflows well enough on their own.
- Positioning: "assign it a ticket... within minutes or an hour it hands you a formal change proposal, tested, with a summary" (kie.ai/blog/what-is-jules) — the product frames itself around async ticket-to-PR, not live pairing.

**Sourcegraph Amp**
- Deliberately "no new UI to learn" — available from terminal CLI or as a VS Code extension, using a thread-based chat model developers already know (medium.com/@jonathanaraney). Threads auto-sync to ampcode.com/threads for every session, with no explicit save step (medium.com/@steph.jarmak).

**Factory Droids**
- Sessions are explicitly portable across "desktop, web, CLI, and IDE" — start on one surface, finish on another (search synthesis, factory.ai/product/web + changelog). "Missions" (launched Feb 2025) give each feature its own fresh worker session with clean context specifically so no single session must hold an entire project's context, which is an onboarding/scaling answer to "how do I keep a long multi-day project coherent" (factory.ai/news/missions).

**Claude Code on the web (claude.ai/code)**
- Very explicit onboarding path: connect GitHub (via GitHub App during browser onboarding, or `/web-setup` syncing your local `gh` CLI token from the terminal), submit first task (code.claude.com/docs/en/claude-code-on-the-web, code.claude.com/docs/en/web-quickstart). Org admins can turn on "Quick web setup" to skip the GitHub App install prompt entirely and auto-create a Default environment — collapsing onboarding to almost zero clicks for end users, at the cost of an org-wide policy decision made once, centrally.
- Defaults are explicit and named: a **Default environment** with **Trusted** network access is auto-created if you don't have one; "installed tools" ship with no extra configuration needed (cloud-environments doc, referenced from same page).
- Config sharing model: environments (network access, env vars, setup scripts) are shared objects usable "wherever you start a cloud session: the web, the terminal, Claude Tag, routines, mobile and desktop." Repo-committed `.claude/agents/*.md` subagents and settings files are the team-shared layer; environment variables are the way to configure a session per-environment rather than editing files. `/config` on the web deliberately routes to account settings rather than letting you set inline session config — pushing all durable config into files committed to the repo or into environment definitions, which is a strong "no config drift" design decision.
- Zero Data Retention orgs are explicitly excluded from `/web-setup` and other cloud features — a real, named trade-off between compliance posture and convenience.

## 2. Day-to-day surfaces: home screen, run listing/triage, notifications, cost, failure surfacing

**GitHub**: Agents tab shows "all sessions for the repository in one place," with one-click links from a session straight to its PR, archiving to keep the list navigable, and log views that **group similar tool calls together to reduce noise**, expandable diffs, and visible bash commands "for full transparency" (github.blog/changelog/2026-01-26). Mid-run, you can send **steering input without stopping the run**, and steering explicitly "consumes AI credits per message" — cost is surfaced as a per-action cost signal embedded in the interaction itself rather than a separate dashboard. No cost/notification details were found in official docs — GitHub does not appear to publish a first-party cost dashboard for coding-agent runs **[gap, possibly unverified]**.

**Cursor**: the Cloud Agents dashboard shows, per run, which environment/Build was used and version history; hovering the repo name surfaces environment details inline in the run view (cursor.com/docs/cloud-agent). Notifications route primarily through **Slack**: `@cursor` mentions in any channel kick off an agent, and the agent posts status updates back into the same thread it was invoked from (dev.to/imaginex; swizec.com/blog). Cost visibility is a **hard spend limit prompt on first use** rather than a running dashard number, and agents run against "API pricing for the selected model," so cost scales with model choice and context size (cursor.com/docs/cloud-agent). Cursor Automations extend the same dashboard to scheduled/event-triggered runs (GitHub, GitLab, Slack, webhook, Linear triggers) for things like PR review or vulnerability scanning (cursor.com/docs/cloud-agent/automations).

**Devin**: the unifying "Progress" tab merges shell, IDE and browser activity into one timeline per session (fast.io/resources/devin-session-tools-guide). Cost/failure surfacing is unusually blunt: Devin bills in **ACUs (Agent Compute Units)**, and multiple independent reviews report **quality degrading past ~10 ACUs in one session** — i.e., cost and quality-of-output are coupled, and a long session is a leading indicator of a stuck agent, not just a cost line item (trickle.so/blog/devin-ai-review). Reddit users explicitly warn that skipping review of Devin's interactive planning phase before letting it run means "you're just burning money" (search synthesis) — the community-derived lesson is that a plan-approval gate is load-bearing for cost control, not optional polish.

**OpenHands**: 2025 UI work added an "automations dashboard," a "recommended rail," an "overview panel," and a "unified commits drawer" (openhands.dev blog) — i.e., the team moved toward a home-screen model that surfaces suggested next actions and consolidates commit history across runs, rather than a flat session list.

**Google Jules**: task-centric, ticket-style model — "audio changelogs" are called out as a specific communication feature, i.e., Jules produces a spoken summary of what changed as an alternative notification surface to reading a diff (search synthesis referencing Jules feature list). Async by design: you're expected to check back "within minutes or an hour," implying the UI's job is answering "is it done yet / what did it decide" rather than live spectating.

**Amp**: **leaderboards** are a distinctive day-to-day feature — engineering leads get visibility into "thread activity and contribution across a workspace" and "which developers are generating the highest-value sessions" (search synthesis on Amp Teams). Failure/decision surfacing is handled by shareable threads containing the "full reasoning trace, tool calls, and file edits" so a reviewer can inspect *how* an agent reached a diff, not just the diff (medium.com/@steph.jarmak). Cost model is prepaid credits, pass-through pricing with no markup, capped so "you'll never be charged more than you prepay" unless auto-reload is turned on — a hard ceiling by default, opt-in overage (search synthesis on Amp pricing).

**Factory**: dashboard has filters plus "disconnected session state tracking" so a dropped connection doesn't lose run state, and sessions can be archived (search synthesis on Factory changelog). Cross-surface sync (desktop/web/CLI/IDE) means the "home screen" concept is really a shared session list rather than tied to one client.

**Claude Code web**: sessions live in a left sidebar at claude.ai/code; each shows a compact diff indicator (`+42 -18`) you can expand into a full diff view with inline comments that get sent to Claude as the next message — turning code review directly into the next prompt. **Auto-fix** is the standout failure-surfacing feature: Claude can subscribe to a PR's GitHub activity and automatically react to CI failures or review comments, deciding per-event whether to apply a clear fix, ask the human (ambiguous/architecturally significant changes), or note-and-skip (duplicate/no-op events) (code.claude.com/docs/en/claude-code-on-the-web). Sessions expire after inactivity and are explicitly marked "expired" in the list rather than silently vanishing; reopening reprovisions a VM and restores conversation history, but **any subagents or shell commands that were mid-flight are not restored** — a named data-loss edge case. No first-party per-session cost dashboard is documented; cost is folded into existing plan rate limits ("no separate compute charge for the cloud VM," but parallel tasks proportionally consume the same shared rate limit) — this is a notably different cost model from Cursor/Devin/Amp's per-token or per-ACU metering.

## 3. Reuse: templates, playbooks, shared prompts/skills, versioning/review

- **Devin Playbooks** are the most mature "prompt as first-class reusable object" pattern found: a playbook has named sections (Procedure, Specifications, Advice, Forbidden Actions, Required from User), is shareable across a team, and Devin's Advanced Mode adds explicit "session analysis, playbook creation and optimization, and bulk knowledge management" tooling — i.e., there is tooling to *mine finished sessions into new playbooks* and to manage many playbooks at scale (fast.io/resources/devin-ai-playbook-guide; docs.devin.ai/release-notes/2025).
- **Amp threads** function as a reuse/review mechanism by being inspectable and shareable end-to-end (reasoning + tool calls + diffs), letting a team learn "how this kind of task should be prompted" by reading a colleague's thread rather than a static template (medium.com/@steph.jarmak).
- **Claude Code**: the documented mental model splits reuse into four distinct primitives with different scopes — CLAUDE.md (always-loaded context), Skills (on-demand procedures selected by description match — "progressive disclosure"), Subagents (isolated side-tasks, defined in repo-committed `.claude/agents/*.md` and auto-picked-up in cloud sessions), and Hooks (deterministically enforced rules, not suggestions) (claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more). The explicit team-sharing guidance: personal preferences go in *local* files, team-wide-but-repo-specific guidance goes in *project-level* CLAUDE.md, and once a few skills/subagents/hooks/output-styles are working together they should be bundled into a **plugin** to share a coherent setup across teammates or projects — i.e., Claude Code's own docs treat "graduate to a plugin" as the versioning/distribution step, analogous to Devin's "graduate to a Playbook."
- **GitHub Copilot**: repo-level "custom agents" can be selected at task-creation time in the Agents panel (github.blog/changelog/2025-08-19), implying config-as-code for agent variants, though GitHub's own docs did not surface details on how custom-agent definitions are versioned or reviewed **[unverified beyond the panel-selection UI]**.
- **Open-source Claude Code config managers** (all found live on GitHub, none from official Anthropic): a cluster of desktop apps has emerged specifically to solve "skills pile up across 4+ config folders with no way to see or manage them" — direct quote from abubakarsiddik31/skill-manager's own README. Notable ones:
  - `jiweiyeah/Skills-Manager` — syncs one skill definition to 32 different AI coding tools via symlinks, local-first, MIT (github.com/jiweiyeah/Skills-Manager)
  - `abubakarsiddik31/skill-manager` — single dashboard to enable/disable/edit/delete skills across tools (github.com/abubakarsiddik31/skill-manager)
  - `xingkongliang/skills-manager` — adds a "Global Workspace" (every skill in every agent's global folder) and an "All Agents" cross-tool overview (github.com/xingkongliang/skills-manager)
  - `dcaponi/claude-manager` — desktop UI specifically for Claude Code skills, agents, plugins, and "agent teams" at both global and project scope (github.com/dcaponi/claude-manager)
  - `rohitg00/awesome-claude-code-toolkit` — a curated index (135 agents, 35 skills, 42 commands, 176+ plugins, 20 hooks, 15 rules, 7 templates, 14 MCP configs, 26 companion apps) — useful as a map of what the community considers the reusable-unit taxonomy (github.com/rohitg00/awesome-claude-code-toolkit)
  - `yibie/skills-manager` — native macOS variant of the same pattern (github.com/yibie/skills-manager)
  - The recurring theme across every one of these projects' own descriptions: **config fragmentation across tools and scopes (global vs project) is the #1 pain point** motivating a whole sub-genre of side-project tooling — strong independent signal that "one place to see and manage all skills/agents across scopes" is a real, currently-unmet need, exactly the space agent-manager (this repo) occupies.

## 4. Team features: identity, per-user credentials, audit, permissions

- **GitHub Copilot coding agent**: access is gated at the org/enterprise policy layer (Copilot policies / AI Controls tab) and again at the repo layer (which repos the coding agent may touch). GitHub's own "agent-management" doc, fetched directly, **does not document** whether agent actions run under a bot identity vs. the invoking user's own permissions, nor does it document audit logging — a real documentation gap worth flagging rather than assuming an answer.
- **Cursor**: repository access requires the *connecting user's own* GitHub/GitLab/etc. credentials — "connect your own source control account under Integrations and make sure you have access to the repository" — i.e., agent actions are scoped to the invoking developer's real permissions, not a shared service identity (cursor.com/docs/cloud-agent). Security/compliance controls named: secrets management, "restrict outbound domains," private network connectivity via Tailscale, and a "central dashboard for oversight and compliance" on top of per-user credentialing (cursor.com/docs/cloud-agent). Enterprise plans add "team hooks and enterprise-managed hooks" implying centrally-pushed, non-overridable config for compliance.
- **Amp**: Enterprise tier specifically adds **SSO** plus volume discounts and enterprise support; Teams tier (below Enterprise) gets shared billing and thread visibility but not SSO — i.e., identity/SSO is explicitly a paid-tier gate, not a given (search synthesis, sourcegraph pricing pages).
- **Claude Code on the web**: identity/permission model is the most explicitly documented of all products surveyed:
  - Two distinct GitHub auth paths (GitHub App vs. `/web-setup` syncing a personal `gh` token) with an explicit warning that **either method grants a cloud session access to any repo the connecting account can see, not just repos the App is installed on** — app installation is for PR webhooks (Auto-fix), *not* an access-control boundary. To actually restrict which repos are reachable, an org must restrict access at the GitHub layer itself (team/repo membership), not inside Claude's settings. This is a specific, non-obvious gotcha worth calling out for anyone assuming "installed on this repo" implies "can only touch this repo."
  - Org-level policy gate: `allow_remote_sessions` must be turned on by an Owner before `--cloud`/`--teleport` work at all; a network failure to verify this policy **fails closed** (refuses cloud session) rather than defaulting open — a deliberate safety choice named in the docs.
  - Session sharing has different default postures by plan: Enterprise/Team sessions default to **Private** vs **Team** visibility with repo-access verification *on* by default; Max/Pro sessions default to **Private** vs **Public**, with repo-access verification **off** by default, and the docs explicitly warn "sessions may contain code and credentials from private GitHub repositories" — check before sharing. This asymmetry (verification on by default for paid-team tiers, off by default for individual tiers) is a concrete, checkable design decision.
  - Auto-fix's PR replies are posted **under the human's own GitHub username** but labeled as authored by Claude Code — a specific identity/attribution design (shared identity, disclosed authorship) distinct from Cursor's fully-scoped-to-user-credentials model or a hypothetical dedicated bot account.
  - Credential handling: git credentials and signing keys are kept **outside** the sandboxed VM in Anthropic-hosted environments, with a proxy authenticating on the session's behalf using scoped credentials — the VM itself never holds long-lived secrets.
  - Zero Data Retention orgs lose access to `/web-setup` and other cloud features entirely, and IP-allowlisted orgs get a hard authentication failure on every Anthropic-hosted cloud session (since those calls originate from Anthropic's infra, not the org's network) unless support grants an explicit exemption — both are named, concrete compliance/feature trade-offs.

## 5. Common complaints and anti-patterns (to avoid)

1. **Uncontrolled cost from unreviewed autonomy.** Devin users on Reddit explicitly warn that skipping review of the agent's plan before letting it execute means "you're just burning money" (search synthesis); Devin's own ACU billing model ties cost directly to session length, and reviews report **quality degrading past ~10 ACUs** — so a long-running, unreviewed session is simultaneously the most expensive and the most likely to be going sideways (trickle.so/blog/devin-ai-review). *Anti-pattern: no cheap, visible checkpoint before an agent is allowed to run long/expensive.* *Design implication: a control plane should make "approve the plan" a first-class, low-friction gate, and should make session cost/duration visible enough to prompt a human to intervene before it's expensive, not after.*
2. **Admin-gated onboarding kills "minutes to first task."** Both GitHub Copilot coding agent and Cursor Cloud Agents require an org admin action (enabling a policy, connecting source control) before any individual developer can start — even a highly motivated developer is blocked on someone else's action (docs.github.com/copilot; cursor.com/docs/cloud-agent). *Anti-pattern for an internal tool: don't require a second person to unblock a first try.*
3. **Config that silently doesn't travel.** Cursor's own docs flag that **personal `~/.cursor/hooks.json` doesn't apply in cloud VMs** because those VMs have no access to your local home directory — a config a developer set up locally simply stops working with no error, only in the cloud context (cursor.com/docs/cloud-agent). *Anti-pattern: config scoping rules that are correct but invisible, so failures look like the agent "forgetting" your setup.* Similarly, Claude Code's cloud sessions don't restore in-flight subagents/shell commands after a VM is reclaimed on expiry — background work can silently vanish (code.claude.com/docs/en/claude-code-on-the-web).
4. **Perceived quality decline eroding trust over time.** Multiple 2025-2026 sources describe GitHub Copilot's coding agent as measurably slower and lower quality since late 2025 (90+ second web spin-ups repeating 10-20 times per session in one report; suggestion acceptance at 35-40% vs Cursor's reported 42-45%) (nxcode.io; opiniondeck.com synthesis). *Anti-pattern: shipping a control plane whose perceived reliability drifts without visible, trackable metrics — teams need their own local signal (success rate, time-to-completion) rather than relying on vendor messaging.*
5. **Access-control assumptions that don't match reality.** Claude Code's docs explicitly warn that installing the GitHub App on a specific repo does **not** limit which repos a cloud session can reach — it can reach anything the connecting account can see. This is exactly the kind of thing an internal team would wrongly assume is a security boundary. *Anti-pattern: conflating "where the agent is configured" with "what the agent can access."*
6. **Config fragmentation across tools/scopes.** The existence of at least six independent open-source "skills manager" projects on GitHub, each describing the same complaint in their own README ("skills pile up across 4+ config folders with no way to see or manage them" — abubakarsiddik31/skill-manager), is strong bottom-up evidence that multi-scope (global/project/per-tool) config sprawl is a widely-felt, currently-unsolved pain point. *Design implication: a single pane that shows global vs. project-level config side by side, across every relevant tool, is validated demand, not speculative.*
7. **Automation triggering unintended side effects.** Claude Code's docs specifically warn that Auto-fix's PR replies are posted as the human's own GitHub account and can therefore trigger comment-activated automation (Atlantis, Terraform Cloud, custom Actions on `issue_comment`) — i.e., an agent posting "under your identity" can accidentally invoke privileged infrastructure workflows you didn't intend to run. *Anti-pattern: granting an agent your identity's write scope without considering what *else* listens for that identity's actions.*
8. **Sharing defaults that leak.** Claude Code's Max/Pro plans default shared sessions to **Public** (visible to any logged-in claude.ai user) with repo-access verification **off** by default — the docs themselves warn to check for credentials/sensitive code before sharing. *Anti-pattern: a "share" button whose default visibility is broader than the sharer is likely to expect.*
9. **Test results contradicting marketing claims.** Independent testing of Devin found it completed only 3 of 20 assigned tasks successfully in one review, contradicting "first AI software engineer" framing (theregister.com/2025/01/23). *Anti-pattern for an internal tool: setting expectations ("this will do full features autonomously") that the actual success rate doesn't support — better to under-promise scope (narrow, well-specified tasks) and let successful runs build trust.*
10. **No first-party cost dashboard forces third-party tooling.** For Claude Code, the absence of a documented native cost dashboard has spawned separate community projects (`phuryn/claude-usage`, Cmotions' Claude Dashboard) purely to visualize token usage/cost from local logs (github.com/phuryn/claude-usage; cmotions.com). *Anti-pattern: leaving cost invisible enough that users must build or install a separate tool just to see what they're spending.*

## Ten Principles for an Internal Agent Manager Used by a 20-Developer Team

1. **No admin-in-the-loop for a developer's first run.** GitHub Copilot and Cursor both gate cloud agents behind an org-admin action before any individual can try one (docs.github.com/copilot; cursor.com/docs/cloud-agent) — this is the single biggest onboarding-speed killer observed. Ship the internal tool so a developer can go from "nothing" to "first successful task" using only their own permissions, with admin controls scoped to *policy* (which repos, which models, spend ceilings) set once, centrally, in advance — not a per-user unlock.

2. **Make config scope explicit and visible in the UI, not just in file paths.** Cursor's silent "personal hooks don't apply in cloud VMs" gap (cursor.com/docs/cloud-agent) and the whole genre of open-source skills-manager tools solving "config pile up across 4+ folders with no way to see it" (github.com/abubakarsiddik31/skill-manager) both point to the same fix: show global vs. project vs. personal config side-by-side, and flag when a scope won't apply in the current execution context, rather than letting it fail silently.

3. **Cost must be visible per-action, not just per-invoice.** GitHub's design of showing "steering consumes AI credits per message" directly in the run UI (github.blog/changelog/2026-01-26), and Amp's prepaid-credit hard cap with opt-in-only overage (Amp pricing pages), are both better patterns than Claude Code's current gap (folded into shared plan rate limits with no native dashboard, which has spawned third-party tools like `phuryn/claude-usage`). Surface running cost/duration on every session card, and hard-cap by default.

4. **A cheap, mandatory checkpoint before a run gets expensive or destructive.** The Devin community's own lesson — "skip reviewing the plan and you're just burning money" — plus Devin's own documented quality drop-off past ~10 ACUs in one session (trickle.so/blog/devin-ai-review), both argue for plan-approval as a default gate, with escalating friction (require re-approval) as session length/cost crosses thresholds, not a one-time approval at t=0.

5. **Treat "reusable prompt" as a first-class, versioned object with graduation path.** Devin's Playbook model (named sections: Procedure, Specifications, Advice, Forbidden Actions, Required from User) and Claude Code's "bundle skills/subagents/hooks into a plugin once they're proven" pattern (claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more) both show the same lifecycle: start ad hoc → notice repetition → promote to a named, shareable, versionable unit. The internal tool should make that promotion one click, not a manual copy-paste into a new file.

6. **Reviewable reasoning traces, not just diffs.** Amp's thread-sharing (full reasoning trace + tool calls + diffs, inspectable by teammates) and its leaderboard for engineering-lead visibility (search synthesis, Amp Teams) show that trust and review scale better when a reviewer can see *how* the agent got to the diff, not just the diff. Store and surface the full tool-call trace per run, and make it shareable/linkable like a PR.

7. **Failure handling should be graded (auto-fix / ask / skip), never silently retried into cost.** Claude Code's Auto-fix explicitly triages events into three buckets — confident fix, ask-human on ambiguity, note-and-skip on duplicates (code.claude.com/docs/en/claude-code-on-the-web) — a good template versus either fully-autonomous retry loops (risk: burning budget on a stuck task, per Devin's ACU complaints) or requiring a human for every failure (kills the async value proposition).

8. **Identity should ride the invoking user's real permissions wherever possible; where a shared identity is unavoidable, disclose it.** Cursor scopes cloud-agent repo access to the connecting user's own credentials (cursor.com/docs/cloud-agent); Claude Code's Auto-fix posts under the human's GitHub identity but labels replies as agent-authored, and explicitly warns this can trigger the human's own comment-activated automations (code.claude.com/docs/en/claude-code-on-the-web). For a 20-person team, prefer per-user OAuth tokens over one shared service account, and if a shared identity is used anywhere, document exactly what else is subscribed to that identity's actions.

9. **Access boundaries must be named exactly, because "installed on repo X" does not mean "can only touch repo X."** Claude Code's own docs had to explicitly correct this misconception for GitHub App installs (code.claude.com/docs/en/claude-code-on-the-web). The internal tool's permission model should be documented (and ideally enforced) at the level developers will actually assume it works — repo scoping, not account scoping — or the docs/UI must correct that assumption loudly.

10. **Sharing/visibility defaults should default to the narrower option, especially for anything that might contain secrets.** Claude Code's own Max/Pro default (Public, repo-verification off) contradicts its own written warning to check sessions for credentials before sharing (code.claude.com/docs/en/claude-code-on-the-web) — an internally-inconsistent default that a 20-person team building its own tool should not copy. Default every session/thread to private-to-team, require an explicit action to widen visibility, and verify the viewer's repo access whenever a session is shared.
